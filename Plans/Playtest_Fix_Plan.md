## 1. 플레이 시간이 너무 짧다

### 1.1 지금 상태 (측정값)
| 항목 | 값 |
|---|---|
| 경기장 크기 | 12×14칸 ~ 26×12칸, 칸 0.5m → **가로·세로 5~14m** |
| 주인공 이동 속도 | 3.4m/s (`PlayerActionSettings.moveSpeed`) |
| 시작점 → 적 거리 | 1-1 기준 5.5m → **직선 1.6초** |
| 탄막 턴 길이 | 8초 |
| 적 체력 | 테스트 적 30, 주황 테스트 적 45 |
| 측정 봇 결과 | 적에게 닿는 데 1.5~3.8초, 모든 맵 2~3턴에 끝 (`Plans/Balance_Report.html`) |

턴은 "적에게 닿으면 즉시 종료"이므로, 거리가 짧으면 패턴을 거의 보지 못하고 끝난다. 전투 전체도 턴 수가 적어 짧다.

### 1.2 제안
**A. 맵 확대 (필수, 사용자 요청)**
- 시작점 → 적 거리를 **18~30m**로 (직선 5~9초, 피하면서 10~20초).
- 방법: 칸 크기 0.5m → 1.0m로 바꾸고 칸 수도 늘린다 (맵툴 한도 40칸 × 2m까지 이미 가능). 스테이지 JSON은 **맵툴(또는 맵툴 코드)로만** 바꾼다.
- 맵툴 검증 추가: "시작점-적 최소 거리"를 칸이 아니라 **미터**로 검사 (기본 15m).
- 함께 고칠 것:
  - 탄 수명·사거리: 멀리 있는 주인공까지 탄이 닿는지 검사 (패턴마다 `수명 × 속도 ≥ 경기장 대각선`).
  - 카메라: 넓은 맵에서 적 방향 표시(화면 밖 표시 ✅ 있음)를 더 크게.
  - 보석 배치: 넓어진 맵에 맞게 재배치.

**B. 적 보호막 (보류 — 사용자 선택 안 함)** — 턴 시작 후 일정 시간 동안 적에게 닿아도 튕겨 나오는 방식. 맵 확대 후 측정 결과가 부족할 때 다시 검토.

**C. 적 이동 (보류 — 사용자 선택 안 함)** — 맵툴에서 찍은 위치 2~4곳을 적이 옮겨 다니는 방식. 위와 같이 보류.

**D. 전투 전체 목표 시간**
| 구간 | 목표 전투 시간 | 목표 턴 수 |
|---|---|---|
| 1-1 ~ 1-2 | 1~1.5분 | 4~5턴 |
| 1-3 ~ 1-5 | 1.5~2.5분 | 5~7턴 |
| 1-6 ~ 1-8 | 2.5~4분 | 6~8턴 |

턴 수는 적 체력·FIGHT 피해·자비 조건(3절)으로 맞추고, 측정 봇이 **접근 시간 ≥ 6초**, **턴 수**를 보고서에 표시한다.

### 1.2.1 실제 적용 (9단계 ✅)
- 8개 맵: 칸 1m, 시작점-적 18~28.6m (1-8은 40칸 한도로 20.6m), 탄막 턴 = 직선 시간 × 1.8 + 4초 (14~19초). 1-1 경기장 6×7m → 20×23m.
- 맵툴 경고: 시작점-적 15m 미만. 스테이지 JSON v2(`theme`·`dialogues`), v1도 읽음.
- 적 체력 30→70, 45→90. 측정: 적 접근 평균 5.0~8.1초 (이전 1.5~3.8초). 상세 표는 `Plans/Action_Balance_Plan.md` "실제 적용된 9단계".

### 1.3 바뀌는 파일 (예상)
- 스테이지 JSON 8개 (맵툴 코드로 재생성), `StageValidator`(미터 거리 검사)
- 패턴 데이터 (사거리 검사), `BalanceMeasurementTests`, `Tools/render_balance_report.mjs` (접근 시간·턴 수 표시)

## 2. 적마다 공격이 하나라 읽기 쉽다

### 2.1 지금 상태
- 스테이지 JSON의 `enemyTurn.patterns`가 `Attack_Stage_1-n` **하나**. 이 안의 `PatternDirector`가 맵 순서대로 쌓인 패턴(1→8개)을 섞어 쓰긴 한다 🟡.
- 하지만 **새 패턴은 처음 2초 혼자** 나오고, 둘째 패턴은 1.6초 뒤에 겹친다. 주인공이 2~4초 만에 적에게 닿으므로 실제로는 **패턴 하나만 보고 끝나는** 경우가 대부분이다.
- 두 적(`Enemy_Test`, `Enemy_Test2`)이 같은 패턴 묶음을 쓴다 → 적의 개성이 없다.

### 2.2 제안
**A. 적별 기술 세트 (`EnemyMoveSet` 데이터)**
- 적마다 기술 3~6개. 기술 = 패턴 1개 이상 + 등장 조건(체력 비율, 턴 수, 자비 진행도) + 색(노랑·빨강·파랑).
- 맵은 "어느 적이 나오는지 + 난이도"만 정하고, 무슨 공격을 할지는 적이 정한다.

**B. 동시 사용 = 겹(레이어) 구조**
| 겹 | 역할 | 예 |
|---|---|---|
| 주 공격 | 계속 압박 | 원형 탄막, 사인파 |
| 방해 | 이동 경로를 막음 | 빨강 벽(정지해야 통과), 파랑 줄(움직여야 통과) |
| 저격 | 가끔 주인공을 노림 (예고 표시 후) | 조준 직선탄 |
| 맵 장치 | 맵툴로 배치한 발사대 | 고정 회전 포탑 |

- 한 턴에 2~3겹이 동시에. 빨강+파랑 동시 금지 규칙(`ColorCombinationRules`)은 그대로 지킨다.
- "새 패턴 2초 혼자"는 **처음 만나는 기술만** 적용하고, 같은 기술의 두 번째부터는 바로 겹친다.

**C. 체력 단계 (페이즈)** — 체력 70%·35%에서 기술 조합이 바뀌고 발사 간격이 줄어든다. 단계가 바뀔 때 적 대사(6절 대화 시스템)와 짧은 연출.

**D. 공격 순서 (콤보)** — "원형 탄막 → 1.2초 뒤 저격 3발"처럼 시간표로 묶은 기술. Pattern Editor에 **시퀀스 탭**을 추가해 시간표를 만든다.

**E. 맵 발사 장치 (보류 ❓)** — 맵툴에서 경기장 위에 발사대를 놓는 방식. 사용자가 접근 시간 대책으로는 고르지 않았으므로, 넓은 맵에서 "적 근처만 위험"하다고 측정되면 다시 제안한다.

### 2.2.1 실제 적용 (9단계 ✅ — A·B·C, D는 9b Codex, E 보류)
- A: 적 데이터에 `signatureMoves`(고유 기술)·`phaseMoves`(체력 단계 기술). 별도 `EnemyMoveSet` 에셋 대신 EnemyData 칸으로 단순화.
- B: 한 턴 최대 3겹, 모든 쌍 빨강+파랑 금지. 새 패턴은 소개 2초만 혼자, 같은 턴 안에 다른 겹 합류.
- C: `DifficultyProfile.phases` (체력 비율 → 겹 추가·간격·탄속), 단계가 오른 턴에 `BattleFeedback.EnemyPhaseChanged` (10단계 대화가 구독할 예정).

### 2.2.2 실제 적용 (9b단계 ✅ — D)
- AttackSequence의 시작 시각·패턴·반복 횟수/간격·지속 시간을 안정 정렬한 시간표로 실행한다. 각 자식에 독립 시드와 난이도 배율을 전달하고 프레임 경계에서 시작/종료를 분할해 처리한다.
- SequencePattern이 Director 안에서 실행되고 자식의 위험 위치를 합친다. 지속 시간 또는 턴이 끝나면 자식의 탄과 예고도 정리한다. 빨강+파랑, 비정상 시간, 중첩 시퀀스는 검증에서 거부한다.
- Pattern Editor 시퀀스 탭: 임시 편집 사본·목록·시간표·시간 슬라이더·그래프 탄의 합성 3D 미리보기·저장/프리팹/카탈로그 등록. 일반 비그래프 패턴은 시간표로 확인한다.
- 주황 적의 phaseMoves에 고리 12발 → 1.2초 뒤 부채꼴 3발씩 세 번 샘플을 도구 코드로 등록했다. 기본 간격에서는 0/1.2/2.4/3.6초에 시작한다. 자식의 발사 간격 30초·지속 6초로 각 발사를 한 번씩 유지한다. 피해·체력 수치는 그대로다.
- 전체 EditMode 199개 통과. PlayMode 결과는 단계 작업 기록에 남긴다.

### 2.3 바뀌는 파일 (예상)
- 새 데이터: `EnemyMoveSet`, `EnemyMove`, `AttackSequence` (ScriptableObject)
- `PatternDirector`/`DirectorPlanner` (겹·페이즈·처음만 혼자), `EnemyData`(기술 세트 참조)
- 맵툴(발사대 배치), Pattern Editor(시퀀스 탭), 스테이지 JSON 스키마 v2 (`emitters`)

## 3. 자비가 너무 빠르다

### 3.1 지금 상태
- `Enemy_Test`: 문턱 2, ACT "응원하기"·"말 걸기" 각 +1 → **2턴이면 자비**.
- `Enemy_Test2`: 문턱 3, "같이 뛰기" +2 → 2턴.
- 자비 보석(`spare`)도 진행도를 올린다. FIGHT를 해도 진행도는 그대로.

### 3.2 제안 — 적마다 "자비 조건" 데이터
**공통 규칙 (모든 적, 사용자 결정):** FIGHT를 하지 않은 턴이 **3번** 쌓이고, **그리고** 아래 적별 특수 조건을 채워야 자비 가능. FIGHT를 하면 그 카운트가 0이 되는지 / 줄어드는지는 적마다 설정.

**적별 특수 조건 (하나 이상, 모두 충족 또는 하나만 충족 선택):**
| 조건 종류 | 예 |
|---|---|
| ACT 순서 | "칭찬하기 → 같이 뛰기 → 기다리기" 순서대로 |
| 탄막 턴 행동 | 쳐내기 5번, 빨강을 정지로 3번 통과, 한 턴 동안 안 맞기 |
| 대화 선택 | 대화에서 특정 선택지 고르기 (6절과 연결) |
| 보석 | 자비 보석 2개 모으기 |
| 상태 | 적 체력 50% 이하일 때만 (반쯤 지친 뒤 설득) |

- **표시:** 적 이름 옆에 "마음" 게이지(또는 단계 아이콘 ○○●). 살펴보기(Check)에서 힌트 문장.
- **자비 보석:** 진행도 직접 증가 → "힌트 1개 공개"로 바꾸는 것을 제안 ❓.
- 데이터 방식: `EnemyData`에 `SpareRule`(조건 목록, `[SerializeReference]`로 종류별 클래스). 전투 코드에 적별 `if` 없이 조건 클래스만 추가하면 늘어난다.
- 이 조건은 전투 상태 머신이 모르는 사건(쳐내기·정지 통과)을 쓰므로 `BattleFeedback` 구독으로 센다 (이미 사건이 다 있음 ✅).

### 3.3 바뀌는 파일 (예상)
- 새 로직: `SpareRule`, `ISpareCondition` + 조건 클래스 5종, `SpareTracker` (순수 C#, EditMode 테스트)
- `EnemyCombatant`(`CanBeSpared`를 규칙으로), `EnemyData`, 적 에셋 2개, `GemRewards`(자비 보석), 상태 표시 UI
- `BattleTexts`(힌트·게이지 문구)

### 3.4 실제 적용 (10단계 ✅)
- 전투별 SpareTracker + 직렬화 조건: 공통 공격하지 않은 턴 3번, ACT 순서, 쳐내기/빨강/파랑 통과 횟수, 안 맞은 턴, 대화 선택, 자비 보석, 적 체력 비율. 모든 조건 충족 시 자비. FIGHT 선택 시 공통 카운트 초기화(적 데이터에서 절반 옵션), 취소·아이템 빈 목록은 턴을 소비하지 않는다.
- 테스트 적: 응원하기 → 말 걸기 + 이야기 듣기 플래그. 도입 선택에서 미뤄도 말 걸기로 플래그를 얻는다. 주황 테스트 적: 같이 뛰기 + 쳐내기 3회. 공통 3턴은 두 적 모두 적용. 규칙 비활성 데이터는 기존 진행도 방식과 호환.
- 자비 보석은 진행도를 올리지 않고 아직 충족하지 못한 조건의 힌트 한 개를 공개. 적 이름/턴 표시의 ●○ 단계와 자비 메뉴 강조, 살펴보기·ACT 결과에 진행 힌트. EnemyData 인스펙터에서 조건 종류 추가/삭제 가능.
- 데미지·체력·공격 수치 유지. 1-1 최소 3턴 자비 시나리오 및 처치/살려주기/패배 봇 회귀 확인.

## 6. 대화 시스템과 툴 (JSON)

### 6.1 목표
- 전투 시작 전, 턴 사이, 체력 단계 전환, 자비 가능, 승리·패배 때 **캐릭터가 서서 대화**하는 장면.
- 선택지와 그 결과(자비 진행, 플래그, 다음 대화)를 데이터로.
- 대화는 **JSON + 전용 툴로만 편집** (스테이지 JSON과 같은 규칙).

### 6.2 JSON 형식 (안)
`Assets/StreamingAssets/Dialogues/dlg_stage_001_intro.json`
```json
{
  "schemaVersion": 1,
  "id": "dlg_stage_001_intro",
  "speakers": {
    "heroine": { "name": "주인공", "anchor": "player" },
    "enemy":   { "name": "테스트 적", "anchor": "enemy" }
  },
  "start": "n1",
  "nodes": [
    { "id": "n1", "speaker": "enemy", "text": "여기까지 온 거야?", "pose": "talk", "camera": "enemy_close", "next": "n2" },
    { "id": "n2", "speaker": "heroine", "text": "싸우러 온 건 아니야.", "pose": "talk", "camera": "two_shot",
      "choices": [
        { "text": "이야기를 들어 준다", "next": "n3", "effects": [ { "type": "spareCondition", "id": "listened" } ] },
        { "text": "검을 든다", "next": "end", "effects": [ { "type": "flag", "id": "hostile", "value": true } ] }
      ] },
    { "id": "n3", "speaker": "enemy", "text": "...고마워.", "pose": "relief", "next": "end" },
    { "id": "end", "end": true }
  ],
  "_tool": { "generatedBy": "DialogueEditor", "toolVersion": 1, "checksum": "sha256:..." }
}
```
- `pose` → 애니메이션(5절), `camera` → 카메라 컷 이름(`BattleCameraDirector`에 등록), `effects` → 자비 조건(3절)·플래그.
- 대사 안 짧은 태그(선택): `{wait=0.4}`, `{shake}` — 텍스트 속도 설정 ✅ 반영.

**연결 — 스테이지 JSON v2**
```json
"dialogues": {
  "intro": "dlg_stage_001_intro",
  "phase2": "dlg_stage_001_phase2",
  "spareReady": "dlg_stage_001_spare",
  "victory": "dlg_stage_001_win"
}
```
적마다 공통 대화는 `EnemyData`에 같은 방식으로 지정, 스테이지 지정이 있으면 그것이 우선.

### 6.3 실행 구조
| 부분 | 역할 | 종류 |
|---|---|---|
| `DialogueDefinition`·`DialogueJson`·`DialogueValidator` | 읽기·검증 (끊긴 연결, 없는 화자, 폰트에 없는 글자) | 순수 C# + EditMode 테스트 |
| `DialogueRunner` | 노드 진행, 선택, 효과 적용 | 순수 C# (조건·효과는 등록식, 적별 `if` 없음) |
| `DialogueState` | 전투 상태 머신의 새 상태 (`BattleStateId.Dialogue`) | 상태 클래스 |
| `DialogueView` | 대사 상자 + 이름표 + 선택지 (기존 `DialogueBox`·`MenuNavigator` 재사용) | UI |
| 카메라·자세 | 컷 이름 → 카메라, `pose` → 애니메이션 | View |

### 6.4 툴 — `Tools ▸ Dialogue Editor`
- 왼쪽: 대화 파일 목록 / 가운데: 노드 목록(또는 연결 그래프) / 오른쪽: 선택한 노드 편집 (화자·대사·자세·카메라·선택지·효과).
- 저장 시 검증 (연결 끊김, 도달 못 하는 노드, **정적 폰트에 없는 글자**) — 실패하면 저장 안 함.
- "미리 보기": 툴 안에서 대화를 한 줄씩 넘겨 보기. "바로 플레이": 해당 스테이지로 전투 시작 (맵툴 M5 방식 재사용).
- 맵툴에서 스테이지마다 대화 파일을 고르는 칸 추가.

### 6.5 주의
- 폰트가 **정적 아틀라스**라 새 대사의 한글이 없으면 □로 나온다 → 툴 검증 + `FontCoverageTests`가 대화 JSON까지 검사. 없는 글자가 나오면 아틀라스 재생성 단계(문서화)를 안내.

### 6.6 실제 적용 (10단계 ✅)
- 설계 형식 그대로 화자 사전·노드·선택지·효과·종료·도구 체크섬을 JSON에 저장. 외부 JSON 라이브러리 없이 표준 DataContractJsonSerializer 사용. Repository는 파일 이름/경로·체크섬을 확인하고 검증된 임시 파일을 교체 저장한다.
- DialogueRunner는 등록한 flag/spareCondition 처리기에 효과를 전달. BattleStateId.Dialogue에서 기존 대사 상자와 목록 메뉴를 사용하고 입력/텍스트 속도를 그대로 적용. 스테이지 대화가 적 기본 대화보다 우선, 파일이 없으면 기존 문구 흐름 유지.
- 도입·체력 단계(다음 플레이어 메뉴에서)·자비 가능·전투 종료 연결. enemy_close/two_shot/player_close 카메라 컷과 복귀. 자세는 12단계 연결 예정이며 미지원 값은 경고한다.
- Tools → Dialogue Editor: 파일/노드/화자/대사/자세/카메라/선택/효과 편집, 되돌리기/다시 하기, 연결·도달·화자·효과·정적 폰트 검증, 한 줄씩 미리 보기, 선택 스테이지에 도입 연결 후 바로 플레이. Stage Editor에 상황별 파일 선택 4칸.
- 편집기 코드로 샘플 5개 생성 및 1-1/1-2 연결. 마음 단계 기호 ●○를 포함해 정적 폰트 갱신(GUID·LFS 유지). 검증: EditMode 196 통과, PlayMode 게임 검사 34 통과·측정 전용 1 제외. Logs/phase10_*.xml 및 scene_phase10_*.png.
